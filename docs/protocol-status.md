# Protocol Support Matrix

## Features at a glance

The reference implementation targets the ECSP V2 family. It was first built
against Omada Network Application `6.2.14.11` with an EAP110 v4-compatible AP
profile, and has since been validated against Controller `6.3.0.111` with a
dual-band Wi-Fi 6 OpenWrt AP advertised as an EAP model of the same generation
(`OMADA_DEVICE_MODEL`, or `auto` to pick the closest model from the radios;
see the [configuration reference](configuration.md#device-identity)).

| Area | Status |
| --- | --- |

| `PRE_ADOPT_REQUEST` handling | ✅ Working |
| TLS management channel | ✅ Working |
| Legacy V2 mutual Device Account verification | ✅ Working |
| Device/system negotiation | ✅ Working |

| Restart without another manual Adopt | ✅ Working |

| Radio capability advertisement | ✅ From `iw list`: channels, widths up to 160 MHz, antennas, wireless modes; DFS channels when the regulatory domain supports radar detection |

| Interference Detection scan | 🟡 On-demand neighbour scan with `iw`; shows in Statistics → Interference Detection |
| Radio/SSID configuration | 🟡 OpenWrt UCI adapter: SSIDs, wireless mode, channel, width (20–160 MHz), Tx power up to the radio's limit, Auto channel range, Wi-Fi country (`OMADA_WIFI_COUNTRY`) |
| SSID security | 🟡 WPA-PSK, WPA2-PSK, WPA/WPA2-PSK and WPA2-PSK/WPA3-SAE, PMF and 802.11r; Load Balance advertises 802.11k (no steering daemon yet) |
| MAC filtering | 🟡 Deny and Allow lists from MAC groups, per SSID and band, kept across restarts |

| SSID VLAN configuration | 🟡 Opt-in OpenWrt UCI adapter |
| Management VLAN configuration | 🟡 Opt-in OpenWrt UCI adapter |
| Client IP/name reporting | 🟡 hostapd association is the source of truth; IPs and names come from DHCP leases, openNDS and passive DHCP/ARP/NDP/mDNS listening on the bridges |
| OpenWrt radio/SSID telemetry | 🟡 Live channel, width and mode, per-SSID stats and channel utilisation via `ubus`, hostapd and `iw` |

| `GET_REQUEST` | 🟡 Defensive unsupported-key responses |
| Notify families | 🟡 Defensive unsupported replies |
| Report family | 🚧 Envelope and protobuf DTOs identified; `reportData` serializer not implemented |
| Switch/gateway/OLT device profiles | 🚧 Planned |

The capability table is intentionally conservative. The agent advertises only
components whose lifecycle is currently understood well enough not to mislead
the controller. On OpenWrt, `OMADA_MAX_SSIDS` is treated as a manual upper
bound; when `iw list` reports no valid multi-interface combinations, the agent
caps the advertised and applied SSID count to one AP interface so hostapd does
not fail the whole radio.

This table tracks **implementation status**, not merely known numeric message
identifiers.

| SET | 🟡 | Envelope/version ACKs plus parsed AP domains; one-off commands without a version (`rogueApScan`) keep the current version; unsupported keys return local error instead of fake success, after the supported keys in the same SET are applied (Validated: a SET with `macFilterAssoc` and an SSID change used to leave the SSID unchanged); common controller defaults such as `ssh`, `lldp`, `ipGroup`, `ipv6Group`, `lanSetting`, `logSetting`, and the scheduler globals are accepted as passive when they do not require OpenWrt changes |
| WLAN/radio config | 🟡 | OpenWrt UCI adapter for basic radios and PSK SSIDs. Radios are matched by their UCI `band` option (`2g`, `5g`, `6g`), not by number, since many boards have radio0 = 5 GHz: the controller's 2.4 GHz settings and SSIDs go to the `2g` radio, and a second `5g` radio (by name order) is 5 GHz-2; a SET for a band no radio has is refused, and the radio number is used only when no `wifi-device` has a `band`. Telemetry reports each radio under the band in its `ubus` `config.band` by the same rule; once any radio has a band, a radio without one is left out of telemetry, as its settings are refused. Startup pruning of stale Auto channel lists uses the same rule, so each 5 GHz radio keeps its own channels. Validated: lab AP (radio0 = 2.4 GHz), a full sync applies each band to its radio and telemetry matches. Inferred (tests only): boards with radio0 = 5 GHz or two 5 GHz radios. Values are written in single quotes with only `'` escaped, so a backslash in an SSID or key is kept (Validated: lab AP, libuci reads them back unchanged). WPA Mode, PMF and 802.11r from the SSID editor (Observed, lab: `pskVer` 1 WPA-PSK, 2 WPA2-PSK, 3 WPA/WPA2-PSK, 4 WPA2-PSK/WPA3-SAE; `pskCipher` 1 Auto, 3 AES; `pmfMode` 1 Mandatory, 2 Capable, 3 Disable; `fastTransition` {`enable11r`, `mobilityDomain`, `keyRrb`}) map to `encryption` (`psk`/`psk2`/`psk-mixed` + `+tkip+ccmp` or `+ccmp`, `sae-mixed`), `ieee80211w` and `ieee80211r`. The SSID's Security (`securityMode`) decides whether a key is used: None (0) is open even if an old key is still sent, WPA-Personal (3, Observed) needs its key, and WPA-Enterprise (2), PPSK (4, 5) and OWE (None with `oweEnable`) are refused rather than created open (codes other than 3 Inferred from the controller's Security list). `pskCipher` 2 (TKIP only, not offered by the editor) and other unknown codes are refused; a leftover `enable11r` on a WPA-PSK SSID is ignored. 802.11r on WPA2-PSK and WPA/WPA2-PSK uses `ft_psk_generate_local=1` (each AP derives the FT keys from the PSK). On WPA2-PSK/WPA3-SAE it uses `ft_psk_generate_local=0` with `r0kh`/`r1kh` built from `keyRrb`, because OpenWrt reads the key holders only when local generation is off and FT-SAE cannot derive keys locally (Observed: OpenWrt 25.12 `/usr/share/ucode/wifi/ap.uc` and `/lib/netifd/hostapd.sh`). Validated: lab, hostapd runs SAE FT-SAE WPA-PSK FT-PSK, the generated hostapd config holds one `r0kh` and one `r1kh` per radio, and clients connect. Unknown: roaming between two APs, and whether a real EAP uses the same key holders (see below). SSID Load Balance (`loadBalance` 0/1, Observed) writes `ieee80211k=1` (neighbour and beacon reports), plus `bss_transition=1` (802.11v) only when hostapd has WNM: `wpad-basic` refuses `bss_transition` and the radio stays down (Observed: lab, wpad-basic-mbedtls 2025.08.26; Validated: 802.11k only, radios up). Nothing moves clients yet: that needs a steering daemon such as `usteer` (Unknown: how a real EAP picks which clients to move). `chanWidth` enum codes map to `htmode` (Observed: 2=20, 3=40, 4=20/40, 5=80, 6=20/40/80, 7=160 MHz); Auto channel uses ACS limited to `channelRange` and usable channels; `OMADA_WIFI_COUNTRY` sets the country (the controller sends none); `wirelessMode` codes (3 b/g, 4 b/g/n, 13 b/g/n/ax, 7 a/n, 10 a/n/ac, 16 a/n/ac/ax; Auto = key absent) select the htmode family, capped at the hardware (Validated: lab, b/g → `NOHT`/`hw_mode=g`, a/n/ac → `VHT80`, Auto → `HE`) |
| SSID VLAN config | 🟡 | Opt-in UCI network interface mapping; dynamic VLAN/Option82 remain rejected unless implemented |
| Management VLAN config | 🟡 | Opt-in UCI device remapping via explicit local target variables |
| Client operations | 🟡 | Reconnect/deauth through hostapd `ubus`; block/unblock and rate-limits through nftables bridge policy |
| LED config | 🟡 | Optional sysfs brightness adapter for `led.enable`; optional trigger adapter for `led.locate`, written in the order Linux LED rules need so the LED keeps its On/Off state after Locate (Validated: lab, Controller 6.3.0.111); `wifiControlLed` remains rejected |

| MAC filtering | 🟡 | SSID editor → MAC Filtering with a MAC group. Three SET keys (Observed: lab, 6.3.0.111): `macFilterGlobal` {`enable`}; `macFilterList` rules {`operation`, `listId`, `ruleId`, `mac`} (a rule without `ruleId` is the group itself); `macFilterAssoc` rules {`operation`, `ssidId`, `band` 0 = 2.4 GHz / 1 = 5 GHz, `listId`, `action` 0 = Deny / 1 = Allow, `type` 0 = MAC group}. `operation` 1 = add, 2 = delete, 3 = update (unchanged members are resent as 3); a delete with `listId` -1 removes every list from that SSID and band. Edits arrive as changes (`configVersionInc`); a full sync (`configVersion`, sent on every reconnect) resends everything with operation 1, so the agent keeps the state, saves it to `.omada-wireless-state-<mac>.json` once `uci batch` succeeds (so a restart keeps it), and resets it on a full sync. A link to a deleted group filters nothing. With an Allow List linked, Deny Lists on the same SSID are ignored (Inferred: the UI offers one mode per SSID); an Allow List with an empty group blocks every client (Unknown whether a real EAP does the same). Applied as UCI `macfilter` allow/deny plus `maclist` on each SSID section; a change rewrites every agent SSID, including ones not in that SET. Refused: OUI profiles (`type` other than 0, Inferred; hostapd matches exact MACs only), other bands (Unknown), unknown codes and malformed MACs. Validated: lab, deny and allow lists reach hostapd (`deny_mac_file` / `accept_mac_file`, `macaddr_acl` 0/1), a group edit alone updates both SSIDs, filter off and group delete clear them. Not yet tested: a real client being blocked or let in (no client was connected) |
| WLAN schedule | 🟡 | Profiles → Time Range, linked in the SSID editor (WLAN Schedule). Three SET keys (Observed: lab, 6.3.0.111): `schedulerGlobal` {`enable`, `mode` 0 (meaning Unknown)}; `schedulerList` rules {`operation`, `profileId`, `ruleId`, `type`, `day`, `startH`, `startM`, `endH`, `endM`} (a rule without `ruleId` is the time range itself; `type` "Everyday", "Weekday", "Weekend" with `day` 0, or "Select Days" with `day` 1 = Monday … 7 = Sunday; Customized sends one "Select Days" rule per ticked day; an edit arrives as `operation` 2 for the old rules plus 1 for the new ones; deleting a range sends one `operation` 2 rule for the range alone); `schedulerAssoc` rules {`ssidId`, `band` 0/1, `profileId`, `action` 0 = radio off during the range / 1 = radio on during the range}, with no `operation`: each rule is the SSID's whole schedule, and no `profileId` means none. Inferred: `operation` 3 = update as for the MAC filter, Weekday = Mon–Fri, Weekend = Sat–Sun, an end before the start runs past midnight, start = end means the whole day. The agent keeps the state (saved with the MAC filter state) and, once a minute while connected to the controller, sets `disabled` on agent SSIDs in the site's local time (the running agent follows a site time zone change: OpenWrt's libc re-reads `/etc/TZ`, Observed) (marked `openomada_schedule_off`, so it only turns back on what it turned off). Changes happen up to a minute after the range edge. Unknown: whether an EAP keeps its schedule while the controller is down (the agent checks only while connected). Refused: other `type`/`day` codes, times outside 00:00–24:00, other bands and actions. Validated: lab, a "Radio On" range outside the current time turns both SSIDs off at once, an edit that covers now turns them back on, the minute check turns them off at the range end (13:05 → 13:05:35), and unlinking or deleting the range leaves them on |
| 802.11 Rate Control | 🟡 | SSID editor → 802.11 Rate Control. Each SSID item carries `rateCtl` and `manageRateCtl` (Observed: lab, 6.3.0.111); 0 = off. Bits 0–11 are the allowed legacy rates (1, 2, 5.5, 11, 6, 9, 12, 18, 24, 36, 48, 54 Mbps), bit 16 = on; `rateCtl` bit 17 = "Require Clients to Use Rates at or Above the Minimum Rate", bit 18 = "Send Beacons at 1 Mbps"; `manageRateCtl` carries one rate bit, the management rate (samples: 24 Mbps minimum with CCK off and require = `0x30F00`, management 18 Mbps = `0x10080`, 5 GHz 36 Mbps = `0x10E00`). OpenWrt sets rates per radio, not per SSID: the agent writes `supported_rates` (allowed rates plus the management rate), `basic_rate` (the management rate, else the lowest allowed rate; with require, every allowed rate too) and `beacon_rate` `10` (2.4 GHz only) on the `wifi-device`, marked `openomada_rates`, and removes only its own options when the control is off. When SSIDs on one radio ask for different settings, the radio keeps its defaults and the agent logs a warning. Inferred: the basic-rate mapping of "require" and of the management rate. Refused: unknown bits, a control that leaves no rate on the band. Validated: lab, hostapd gets the rates on both radios (2.4 GHz 18–54 Mbps with 1 Mbps beacons, 5 GHz 36–54 Mbps) and both APs stay up; turning it off restores OpenWrt's defaults. Note: OpenWrt's default already leaves out 802.11b rates (`legacy_rates` 0), unlike an EAP. Not checked: rates on the air (needs a sniffer) |
| Radio advanced | 🟡 | `loadBalance_*` → UCI `maxassoc` (hostapd `iface_max_num_sta`), `rssi_*` → `rssi_reject_assoc_rssi`, `qosConfig_*.uapsdEnable` → `uapsd` on agent-managed SSIDs; disabled limits remove the option. Validated: lab, values reach `/var/run/hostapd-phy0.conf` and are removed again. Other `qosConfig_*` WMM/EDCA fields and `wirelessAdv_*` (OFDMA, beacon/DTIM/RTS) are accepted without local changes |
| Network Check | 🟡 | Components `ping`/`traceroute`/`dnslookup`/`arptable` (`1.0`) show Tools → Network Check. SET keys carry `cmdId`, `dest`, `additional{cnt, pktSize}`. Output goes back as plain `NOTIFY_REQUEST` (type 80; `NOTIFY_REQUEST_V2` from an AP is rejected with "Not supported device type: ap") with `sub=5` (TROUBLESHOOTING), `nre=1`, `ctnt={cmdId, troubleshooting{msg, bof, seq, finish}}`; `msg` must be base64 because the UI decodes it with `atob` (Validated: lab, 6.3.0.111) |
| SNMP | 🟡 | Component `snmp` (`1.0`, advertised when `snmpd` is installed) shows Config → Services → SNMP. SET key `snmp` carries `location`, `contact`, `v1v2cEnable`, `community`, `v3Enable`, `v3Username`, `v3SecurityLevel` (0 noAuthNoPriv, 1 authNoPriv, 2 authPriv), `v3AuthMode` (1 MD5, 2 SHA), `v3Password`, `v3PrivacyMode` (1 DES, 2 AES), `v3PrivacyPassword`. The v3 level/mode fields and privacy password are sent only when the AP lists component `service` >= `1.1` (`ApImage.supportSnmpV3Plus`); otherwise just `v3Username`/`v3Password` arrive, so the agent advertises `service` `1.1` with `snmp`. Applied to `/etc/config/snmpd` (read-only access); snmpd is stopped when both versions are off (Validated: lab, 6.3.0.111, `snmpget` v2c and v3 authPriv SHA/AES)
| LLDP | 🟡 | `devCap.supportLldp=1` with components `lldp` and `lldpInform` (`1.0`, advertised when `lldpd` and `lldpcli` are installed) shows the per-AP LLDP switch (Observed: 6.3.0.111 model templates list all three for EAPs). SET key `lldp` is `{"enable": 1|0}`; the controller resolves the per-AP and site settings itself. On: `lldpd.config` gets `enable_lldp=1`, CDP/FDP/SONMP/EDP off, `interface` = the LAN bridge's wired ports, and the package's placeholder LLDP-MED `lldp_location` is removed; lldpd is enabled and restarted. The chassis ID is a LAN port's MAC (subtype MAC), so on devices whose ports have random MACs it is not the device MAC. Off: lldpd is stopped and disabled. While lldpd runs, inform key `lldp` carries `{"lldps": [{"port": <OMADA_LAN_PORT>, "neighbors": [{"chassisId", "portId", "name", "description", "capabilities"}]}]}` from `lldpcli -f json0 show neighbors` (cached 30 s). `capabilities` is 8 characters of `0`/`1` for station, DOCSIS, telephone, router, WLAN, bridge, repeater, other; a MAC chassis ID is sent as `AA-BB-CC-DD-EE-FF` (Inferred: matches how the controller writes device MACs) |
| Site time zone | 🟡 | SYSTEM_NEGOTIATION carries `timeSetting` (`timeZone`, `date`, `time`, `ntpEnable`) and `dst` (`enable`, `start`, `end`, `offset`) at every connect. `timeZone` is the site's standard UTC offset in minutes plus 720 (Observed: 1050 for UTC+05:30; the zone name is not sent). The agent writes the offset as a POSIX TZ string to `system.@system[0].timezone` (e.g. `<+0530>-5:30`), removes `zonename`, and reloads `/etc/init.d/system`; nothing is written when it already matches. `dst` carries `enable`, `offset` (seconds) and the next `start`/`end` as Unix times (Observed: London site → last Sundays of March and October 2027, 01:00 UTC); they become POSIX `Mm.w.d/time` rules, e.g. `<+00>0<+01>-1,M3.5.0/1,M10.5.0`. A transition on one of the last 7 days of a month is taken as "last" (Inferred: the UI offers First to Fourth and Last). Rules that are not "Nth weekday of the month" (some years in Chile or Israel) are approximated until the controller sends the next period. Out-of-range `dst` values are ignored (standard offset only); a SET without `dst` keeps the daylight-saving rules already on the AP. Saving the site's time settings sends a live SET with `timeSetting` and `dst`. NTP and the clock are left alone. `OMADA_CAP_TIMEZONE=false` turns it off (Validated: lab, 6.3.0.111, India → `<+0530>-5:30`, London with Auto DST → rules above; London/Sydney/New York rules match tzdata for 2026–2029) |
| IP Settings | 🟡 Opt-in | Device Config → IP Settings sends SET key `lanSetting` (`connType` 0 static / 1 DHCP, `ipAddr`, `netMask`, `gateway`, `preferredDNS`, `alternateDNS`, `useFallBack`, `fallBackIp`, `fallBackMask`, `fallbackGateway`). With `OMADA_CAP_IP_SETTINGS=true` it is applied to `network.<lan>` 2 s after SET_RESPONSE. A detached watchdog restores the whole previous `/etc/config/network` (so other network edits made in that window are reverted too) after 180 s unless the agent opens a TCP connection to the controller from the new address. The ECSP session is restarted so it binds to the new address. After a rollback the controller still holds the bad setting and resends it on a full sync, so the agent skips a change it rolled back (until reboot). DEVICE_NEGOTIATION reports the running `lanSetting`. DHCP fallback: the fallback address is stored as `network.<lan>.openomada_fallback` (+ `_gateway`) and reported back; while DHCP has no lease for 30 s the agent adds it to the LAN device with `ip` (plus a default route through the fallback gateway if none exists) and removes it once a lease arrives. The 30 s delay is our choice (Inferred: real EAP timing unknown). If `ip addr add` fails, nothing is recorded and the agent tries again after another 30 s (Inferred: unit tests only). Changing only the fallback address swaps it at once (Inferred: unit tests only); writing the fallback options does not restart the LAN interface (Validated: lab AP, OpenWrt 25.12, interface uptime kept counting). (Validated: lab, 6.3.0.111, static .2→.3→.2, unreachable subnet rollback, resend after rollback skipped) |

## Parked work

Known gaps that are deliberately not being worked on now, and why.

| Item | Why it is parked | What would unblock it |
| --- | --- | --- |
| Guest logout (portal logout domain) | The controller sends `controllerSetting.logoutDomain` (acknowledged, not applied). What a real EAP does when a guest opens it (redirect, record removal, `EVENT_PORTAL_AUTH`) is Unknown. | Observe it on a real EAP, then map it to openNDS deauthentication (est. 2 h). |
| Client steering (`usteer`) for Load Balance and Band Steering | Load Balance only advertises 802.11k/v; nothing moves clients. `usteer` would: nudge clients off a weak AP, fill the 802.11k neighbour list from other APs running it, and could back Band Steering (`bandSteerMode`). It only knows APs that run `usteer`, so a real EAP is not in its lists, and polite 802.11v moves need the full `wpad` package (`wpad-basic` lacks it). Whether it is needed at all is Unknown until the home roaming test. | The home roaming test (below) shows clients staying on a far AP with 802.11r on. Then add it as an opt-in: install `usteer` and full `wpad`, map Load Balance and Band Steering (est. half a day). |
| Switch and other device profiles | The agent reports itself as an AP in several places (`device: "ap"`). A device-neutral refactor is the groundwork for switch profiles; it changes nothing visible for an AP. | A concrete switch target to test against (est. one day for the refactor). |

| Conditional SSID Broadcast Control (SSID item `ssidCondCtrl`) | SSID editor → Advanced → Conditional SSID Broadcast Control: pauses the SSID while the AP's uplink gateway or the internet is unreachable and resumes it afterwards, with an Up Delay and a Down Delay (10–300 s, default 30). The SSID item carries `ssidCondCtrl` {`ssidCtrlEnable`, `uplinkTrackType`, `upDelayTime`, `downDelayTime`}; the lab controller does not offer the option for the agent, so it is always sent off (Observed). Inferred: the controller offers it only to APs reporting a newer `ssid` component than the agent does, and raising that version would also claim other SSID features. The agent ignores the item. OpenWrt can do it (turn the SSID off with a marker, as for the WLAN schedule), but the check must keep running while the controller is unreachable, which the schedule's tick does not. Unknown: what an EAP checks for "uplink" and "internet", and the `uplinkTrackType` codes. | Test it on a real EAP (see below), then build it as an opt-in (est. half a day) and only then raise the reported `ssid` component version. |
| Prohibit Wi-Fi Sharing (SSID item `prohibitWifiShare`) | SSID editor → Advanced → Prohibit Wi-Fi Sharing: stops connected clients from sharing the Wi-Fi onward to other devices. The SSID item carries `prohibitWifiShare` (Observed: always `false` in the lab). Inferred: the controller treats the agent's reported `ssid` component version as supporting it, and shows the option where the controller edition allows it, so turning it on would report success while the agent ignores it (a known gap in "advertise only what works"). How an EAP enforces it (for example by dropping traffic whose TTL shows it was forwarded by a client) is Unknown. | Test it on a real EAP (see below), then build the same on OpenWrt (est. 1–2 h if it is TTL-based), or refuse the option while it is unsupported (est. 20 min). |
| SET keys not seen yet | Keys the agent does not know are refused with a local error, after the known keys in the same SET are applied. Settings not used in the lab yet (for example SSID rate limits, band steering, roaming, ACL, mesh, reboot schedule, device account) may send such keys. | Turn each setting on in the lab controller, capture the SET, then implement it, accept it as passive, or keep refusing it (est. 10–15 min per key to capture). |

## Waiting for a real EAP or switch

These need a real Omada EAP or switch, or a second AP, next to the agent. Run them on a lab controller, never a production one.

| Test | What to check |
| --- | --- |
| Portal logout | On a real EAP, open the controller's logout domain as an authorised guest: where does it redirect, is the guest record removed, is `EVENT_PORTAL_AUTH` sent? (est. 10 min) |
| Management VLAN | Set a management VLAN on the AP and confirm it stays reachable from the controller, and that a bad VLAN rolls back (est. 10 min) |
| Fixed-IP reservation | Reserve a fixed IP for the AP in the controller and confirm the AP gets it over DHCP (est. 10 min) |
| MAC filter on a real client | Put a phone's MAC in a group on a Deny List: is the phone dropped and refused? Then switch to an Allow List with only that phone: does it connect while other devices are refused? (est. 10 min) |
| 802.11r roaming | With two OpenWrt APs, then an OpenWrt AP and a real EAP, on one 802.11r SSID: does a client roam with FT authentication (`logread` shows `FT`) rather than a full handshake, for both WPA2-PSK and WPA2-PSK/WPA3-SAE? A full handshake between the EAP and the agent means the EAP's key holders differ from ours. Also check plain WPA-PSK and PMF Mandatory. Then, with Load Balance on, walk away from one AP and stand next to the other: does the phone move by itself, or stay on the far AP until the signal drops out? Staying means a steering daemon (`usteer`, see Parked work) is needed (est. 40 min) |
| LLDP neighbours | With the AP cabled to an Omada switch: do the switch's chassis ID, port and capabilities show for the AP in the controller, do they clear after LLDP Off, and which chassis ID does the switch see for the AP? (est. 10 min) |
| WLAN schedule while the controller is down | Link a time range to an SSID on a real EAP, stop the controller, and cross a range edge: does the EAP still turn the SSID off or on? The agent checks the schedule only while connected (est. 20 min) |
| 802.11 Rate Control on the air | With a Wi-Fi sniffer (monitor mode), check that beacons and data stay at or above the minimum rate, that "Send Beacons at 1 Mbps" sends beacons at 1 Mbps, and compare the basic rates with a real EAP using the same settings; the agent's mapping of "require clients" and the management rate to basic rates is Inferred (est. 30 min) |
| Prohibit Wi-Fi Sharing | On a real EAP with SSH on: record its firewall, bridge, traffic-control and kernel settings before and after turning the option on; then let a client share its connection as a hotspot and check whether a second device behind it gets internet, with the option on and off (est. 20 min) |
| Conditional SSID Broadcast Control | On a real EAP, try "Uplink" and "Internet": cut the gateway, then only the internet, and time when the SSID goes off and back on against the delays; capture what the EAP sends to check connectivity (est. 20 min) |
| Radio mapping on other boards | On an OpenWrt board whose radio0 is 5 GHz, and on one with two 5 GHz radios: do the controller's band settings and SSIDs land on the right radio, does telemetry report each radio under its band, and does startup keep each 5 GHz radio's own Auto channels? The lab AP has radio0 = 2.4 GHz, so this is tested by unit tests only (est. 15 min) |

## Capability policy

A protocol component should not be added to the advertised component map merely
because its name/version is known. It should be advertised only after the agent
can safely process the controller behavior that enabling the component causes.

## MAC serialization policy

The agent keeps MAC addresses internally in normalized lower-case colon form for
comparison and merging. Any MAC emitted toward Omada is converted at the
boundary to `AA-BB-CC-DD-EE-FF`; this includes ECSP headers, `mainMac`, client
stats, SSID BSSID values, RADIUS Calling/Called-Station-Id values, and openNDS
External Portal redirect parameters.
